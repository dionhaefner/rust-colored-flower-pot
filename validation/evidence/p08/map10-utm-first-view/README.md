# Why the first UTM viewport is slower than subsequent pans

This investigation uses the same original EPSG:32632 Sentinel-2 COGs, zoom-13 viewport, three pinned CPU cores, three Rust raster workers and equal 160 MiB aggregate logical cache as the [qualified UTM run](../map10-utm-geometry/README.md). The service starts fresh for each trial, but the OS disk cache is warm. "First view" means the time until **all 12 tiles** in a 1024×768 viewport arrive. Each later horizontal pan adds three tiles; the downward steps add four. The client limits each session to six in-flight HTTP requests. RGB reads three independent TIFFs per tile.

The qualified three-trial medians are [in the summary](summary.json): first-view speedups over Python are 3.06×/4.42× for one user, 3.94×/5.22× for four, and 5.33×/6.09× for eight (singleband/RGB). The equivalent pan p50 speedups are much larger because the reader has opened the sources, initialized coordinate operations and decoded nearby blocks; the Rust application cache and idle tile-neighbor prefetch can serve newly exposed tiles. GDAL performs source decoding in both services, so its cold work limits the first-view advantage of the Rust sampling path. These are server-side viewport-completion timings, not browser paint or truly cold disk measurements.

A temporary `TC_PROFILE_RASTER` instrumented build measured the first three completed RGB band reads in a one-user service: the coordinate/transform stage took 33.7–37.8 ms per band and the following source-window/block stage 24.9–27.4 ms. After those first reads, median stages over the remaining profiled bands were about 0.69 ms for coordinates, 0.80 ms for source windows, 1.47 ms for four-sample interpolation and 0.44 ms for GDAL's final average. The coordinate stage includes CRS setup and transformer construction; the source-window stage includes bounds checks and COG block reads. These are **per-band stage times**, some of which overlap across three workers; they are not additive viewport wall time. The temporary instrumentation was removed after diagnosis. Raw logs remain in ignored `validation/artifacts/map10-utm-first-profile-stages/`.

## Prefetch check

[Three alternating Rust A/B trials](prefetch-ab-report.json) used the same executable and differed only in `TC_PREFETCH_TILE_RING`. All 206 distinct decoded images were exact. Disabling prefetch did not give a robust first-view gain: one-user RGB median moved 158.85→151.90 ms, while eight-user RGB moved 731.15→755.58 ms, with mixed individual trials. It made one-user RGB pan p50 7.01→26.35 ms and eight-user RGB pan p50 56.67→62.00 ms. Retain prefetch. The A/B executable included dormant opt-in profiling hooks, so its hash differs from the qualified binary; the hooks were disabled for this comparison. No image or production-path change was retained.

The most plausible next work is to reduce repeated coordinate setup and duplicate block decode **without merely moving the cost to service startup**. Reusing coordinate grids across aligned RGB bands saves only the warm coordinate portion (roughly 0.7 ms per band in this profile), so it is unlikely to close the first-view gap alone. A source-aware preload could shorten time after service readiness, but would spend the same work at startup and cannot know a user's first viewport without a hint. Faster unique-block decoding or a more efficient first-view raster pipeline may help more, but requires a separate measured implementation and the RW-046 image checks. Progressive client display can improve time to first visible tile while leaving full-viewport completion unchanged. No first-view speedup beyond the qualified result is claimed here.
