# Handoff: original UTM first-viewport diagnosis

Date: 2026-09-28. The qualified original-COG UTM fast path and its current performance claim remain as in [the geometry-cache handoff](map-performance-utm-geometry.md). This task measured why first-view gains are smaller and tested prefetch as a possible cause. [Retained evidence](../../validation/evidence/p08/map10-utm-first-view/README.md) links the compact summary and the three-trial raw A/B report.

The first viewport comprises 12 tiles per user and three independent TIFF band reads per RGB tile; later pans add only three or four tiles. With a fresh service but warm OS disk cache, the first three completed RGB band reads spent roughly 35 ms each in coordinate/transform setup and 25 ms each in source-window/block work. Warm medians for these stages were about 0.69 and 0.80 ms per band. Per-band work overlaps across the three workers; the measured first-view completion is 149.82 ms one-user RGB and 698.23 ms eight-user RGB versus Python 662.21 and 4,254.53 ms. The three-trial prefetch A/B found no robust first-view gain from disabling it, and one-user pan worsened about fourfold. Keep `TC_PREFETCH_TILE_RING=1`.

Temporary opt-in source instrumentation was removed. `validation/tools/p08_rust_ab.py` gained optional workload selectors and a `--candidate-no-prefetch` diagnostic switch; its default reproduction behavior is unchanged. No production image or raster algorithm changed in this investigation. Follow-up candidates: reduce unique COG decode cost, avoid duplicate concurrent block misses, or profile a source-aware prewarm with startup time included. Coordinate-grid sharing across RGB bands is likely a small gain at the measured warm stage cost. Keep the first-view and pan claims distinct, and rerun image and performance qualification for any actual candidate.
